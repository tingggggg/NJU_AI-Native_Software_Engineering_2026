## 核心論點

- Agent 讓「目標明確的程式碼」變得極便宜,瓶頸往上游移:需求、產品設計、架構成為生產力的槓桿,不認真對待就是堆 AI Slop。
- 架構是「跳出問題看問題」:選一種表示,就是選擇讓哪些事情變容易。
- 架構決定的是:保留哪些資訊、把依賴放在哪裡、未來改動付出什麼代價。

## 1. 需求為什麼難

- 三類困難:需求難對齊(客戶只會自然語言)、方案難選擇(可行方案多、成功樣子難預知)、實作與返工貴。
- 教務系統的泥潭:各方需求互相衝突、客戶說不清規則、例外永遠存在(轉專業、交換、緩考、課程替代)。
- MVP 現在很容易做,也確實能逼出沒說出口的需求,但會帶來「駕馭了 AI」的錯覺。AI 不是銀彈:複雜需求、例外規則、持續變更都還在。
- **需求變更會穿透整個 dependency graph;已作出的舊決定會變成新需求的約束。**

## 2. 架構的原則

- 把**容易變化的設計決策藏在模塊內部,讓一次變化只影響一個地方**(Parnas 1972)。
  - 論文的例子(KWIC 索引):按處理步驟切模組(輸入 → 位移 → 排序 → 輸出),每個模組都知道資料怎麼存;資料改存檔案時全部要改。改成每個模組藏一個秘密(行怎麼存、位移結果是複製還是只存索引),同樣的變更只改一個模組。兩種切法第一天都能跑,差別在之後要改什麼。
  - 交易系統的例子:策略只透過 `best_bid()`、`depth(5)` 問 order book,不直接走訪內部的 `std::map`;之後為了延遲換成按 tick 索引的陣列,策略一行都不用改。
  - 注意:成員設成 `private` 不等於資訊隱藏。getter 若回傳 `const std::map&`,呼叫端仍然依賴「它是個 map」。
  - 檢驗法:挑一個最可能變的決定,數數有幾個地方知道它。

KWIC 按「秘密」切的參考拆法,每個模組藏一個會變的決定:

| 模組 | 藏起來的決定 |
| --- | --- |
| Line storage | 行怎麼存(全放記憶體?存檔案?字元怎麼打包?) |
| Circular shifter | 位移結果是複製一份,還是只記「第幾行、從第幾個字開始」 |
| Alphabetizer | 一次排好,還是需要時才排 |
| Input / Output | 輸入輸出的格式 |

其他模組只能透過函式問「第 i 行的第 j 個字是什麼」,不知道答案怎麼存。

- 再小的程式也有架構。要問:資料怎麼穿過各階段?換一種輸入要改到哪裡?

## 3. 三個例子

**10 行:非遞迴河內塔**

| 表示 | 一句話 | 代價 |
| --- | --- | --- |
| 數學規律 | 把遞迴樹壓縮成規律 | 依賴問題的特殊結構 |
| 任務堆疊 | 把遞迴展開成待辦事項 | 顯式管理未完成的工作 |
| 抽象機器(frame 帶 `pc`) | 把函式執行機制顯式化 | 要懂遞迴如何被機器執行 |
| 多分支寫法 | 對稱規則展開成多個 case | 能跑,但仍要解釋規則 |

檢驗標準:改需求時,哪些知識能保留?

**2,000 行:Excel 公式版 QR Code**

- 直接寫公式又長又脆弱。真正要做的是編譯器:Python 構造 IR(帶型別的表達式 DAG,語義獨立於儲存格位址),再生成 Python 與 Excel 兩個後端。
- 好處:每種需求變更有自己的落點(Excel 版本歸目標能力、位置歸佈局、算法歸子圖替換、新輸入歸輸入綁定);兩個後端可以互相比對驗證。

> 📷 圖:一份中間語言、兩種執行方式:生成時構造程式,執行時比對兩個後端的結果(見 [slides6](https://jyywiki.cn/GSE/2026/slides6.html) 第 26 張)

**500,000 行:教務系統**

- AI 直接做的 MVP:業務邏輯擠在幾個大檔案,新增功能像拆盲盒。
- CRUD 的問題:「當前狀態」= 歷史事實 + 當時的規則 + 依規則作出的決定,三者混在一起,依賴關係沒被管理。只留下 `can_graduate = true`,以後分不清是特批還是算錯。
- 語義也會變:系改成學院,`dept_id` 沿用或新開都是在承諾一種業務語義(名字、身份、當時的隸屬是三件事)。
- 程式可以重寫,歷史不能憑空補出來;沒保存的依據,AI 也推不回來。

## 4. 解法:把依賴變成 first-class citizen

> 📷 圖:Event Sourcing:只追加已接受的事實,由事件歷史投影出多種視圖(見 [slides6](https://jyywiki.cn/GSE/2026/slides6.html) 第 40 張)

|  | CRUD | CQRS | CQRS + Event Sourcing |
| --- | --- | --- | --- |
| 中心 | 當前紀錄 | 分離讀寫模型 | 保存歷史、分離讀寫 |
| 能力 | 直接查詢與更新 | 按角色組織查詢 | 可追溯與重算 |
| 代價 | 歷史能力要另建 | 要定義視圖同步契約 | 要管理事件版本與重放 |

- **Event Sourcing**:只追加已被接受的事實(請求不等於事件),狀態由 replay 得到。重放只重建視圖,不重發通知,也不拿新規則改寫既成決定;要改正式結論得走新的審核。
- **CQRS**:寫端表達意圖並檢查約束,讀端按使用者組織資訊。可以單獨使用,不一定要搭 Event Sourcing。
- **DDD**:業務概念決定軟體邊界。「學生」在選課、財務、畢業審核各是不同模型,各自成為限界上下文。

## 5. 實踐要點

- 結論帶著依據:輸入版本 + 規則版本 + 結論 + 審批依據。
- 雙時態:分開記「現實生效的時間」與「系統得知的時間」。
- 用業務不變量劃一致性邊界(搶最後一個名額必須原子完成)。
- 先做模塊化單體再拆服務;遷移用 Strangler Fig,從一條業務鏈開始,缺失的歷史不偽造。
- 不必全盤套用:簡單資料維護照樣 CRUD。
