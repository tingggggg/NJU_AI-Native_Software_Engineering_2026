## 核心論點

- 與其除錯,不如證明程式符合規格,並讓電腦檢查證明(McCarthy 1962)。
- 對程式設計師來說邏輯太難,狀態機比較好懂:窮舉所有可達狀態,本身就是一種證明。
- 形式化的價值,取決於能不能用比實作更簡潔、更獨立的方式表達「正確」。決定「正確是什麼」仍是最難的部分。

## 1. 測試策略的 Single Source of Truth

- 光分好 `unit / module / system` 目錄不夠。新增一類測試時,目錄、CI、文件、執行腳本要改幾處?這是架構問題。
- 做法:在文件裡放一張表(範圍、層級、執行器、參數、標記),人能讀、agent 能維護、CI 能驗證、執行器直接消費。CI 與本地共用同一個入口。
- 表宣告「怎麼跑」,倉庫提供「有什麼」,兩邊互相核對。CI 要獨立掃描倉庫,才抓得到沒登記在表裡的測試;只遍歷表會整片漏掉。

## 2. Hoare 邏輯與不變式

- Hoare 三元組 {P} C {Q}:從滿足前置條件 P 的狀態出發,若程式 C 終止,結果滿足後置條件 Q。例:{x = n} x := x + 1 {x = n + 1}。
- 迴圈靠不變式 I,用一個命題概括任意多輪執行:

| 步驟 | 要證什麼 |
| --- | --- |
| 初始化 | P 能推出 I |
| 保持 | 迴圈條件成立時,執行一次迴圈體後 I 仍成立 |
| 退出 | I 加上迴圈條件不成立,足以推出 Q |

- 說來容易證起來難(例:Boyer–Moore 多數投票)。所以形式化方法多半用來證明演算法,而不是證明軟體。

## 3. 狀態機與 model checking

- 對有限狀態模型,從初態開始加入所有後繼,直到沒有新狀態。得到的集合包含初態且對轉移封閉;裡面沒有壞狀態,就證明了安全性。「所有可達狀態都在這個集合裡」本身就是歸納不變式。例:兩個執行緒各自讀取、加一、寫回同一個變數,窮舉所有交錯就會找到結果不是 2 的狀態。
- 問題是狀態爆炸:元件數線性增長,組合狀態數指數增長。應對方式的演進:

| 年代 | 技術 | 想法 |
| --- | --- | --- |
| 1981–82 | Model checking | 把驗證變成演算法 |
| 1990 | Symbolic model checking(BDD) | 用布林公式表示一整組狀態;狀態數巨大,表示它的資料可能很小 |
| 1999 | Bounded model checking | 把「k 步內是否有錯誤執行」交給 SAT;有解即反例,無解只保證界內安全 |
| 2000 | CEGAR | 先查粗抽象,反例若不可能發生就補回細節 |
| 2011 | IC3 | 逐步生成歸納引理,自動找出不變式或反例 |

- 走到這裡,原本要程式設計師想出來的不變式,也成了演算法搜尋的對象。

## 4. 三條「證明」路線

**Model-based:TLA+**

> 📷 圖:兩階段提交的 TLA+ 模型、抽象規範與 TLC 檢查結果(見 [slides12](https://jyywiki.cn/GSE/2026/slides12.html) 第 14 張)

- 靠 refinement 把簡化模型的正確性帶回真實系統:實作的每一步對應模型的一步(或停頓)。

**Path-based:KLEE(符號執行)**

> 📷 圖:符號執行把 2^32 個輸入合併成 3 條符號路徑,每條路徑一個約束(見 [slides12](https://jyywiki.cn/GSE/2026/slides12.html) 第 15 張)

- 同一路徑上的整類輸入共用一個路徑約束 PC。查「PC 且性質不成立」:有解就是反例,無解就證明這條路徑上的輸入都滿足性質。

**Proof-based:CompCert 與 seL4**

- CompCert 證明編譯保留程式語義(約 3 人年、4.2 萬行 Coq,其中 76% 是證明);seL4 證明核心的 C 實作符合抽象規範(約 25 人年、20 萬行證明腳本)。
- 為什麼是編譯器和核心:它們是大量軟體的共同基礎,證明昂貴,但每次編譯、每次系統呼叫都反覆受益。

## 5. Proof assistant 與 Curry–Howard

> 📷 圖:Proof assistant 的工作台:已知什麼、還要證明什麼,每一步只能用允許的推理規則(見 [slides12](https://jyywiki.cn/GSE/2026/slides12.html) 第 18 張)

- Proof assistant 是鐵面無私的回饋機制:只允許按規則操作。Tactic 或 AI 負責構造證明,最終的證明物件由 kernel 獨立檢查。
- 邏輯操作對應到目標的改寫:

| 要證的命題 | 操作 | 目標變成 |
| --- | --- | --- |
| 存在一個 x 滿足 P | 選定一個 A | 證明 P(A) |
| 所有 x 都滿足 P | 任取一個 x | 證明 P(x) |
| P 蘊含 Q | 把 P 加入已知 | 證明 Q |
| 對所有自然數成立 | 歸納 | 分別證明 P(0) 與 P(n) 推出 P(n+1) |

- Curry–Howard:命題即型別,證明即程式。證明 P 蘊含 Q 就是構造一個 P → Q 的函式;歸納證明就是遞迴程式。遞迴必須終止,否則 f(n) = f(n) 能假裝回傳任何命題的證明。

## 6. AI 與形式化

- LLM 讓形式化驗證在更大規模上變得可行;講者以自己博士論文裡擱置的猜想為例,說明連證明也開始能交給模型。但提出問題的經驗與解決問題的信心,仍來自 CS 的訓練。
- 防止「證了個寂寞」:形式化的規格也可以執行、可以測試。
- 可能的未來:proof-carrying code(OSDI '96),程式碼附帶可由機器檢查的證明。
- 沒有銀彈:「不會 crash」「沒有記憶體越界」這類性質能簡潔表達;「領導滿意的教務系統」「自然舒適的動畫效果」很難形式化。需求本身也要經過原型與回饋才成形。
