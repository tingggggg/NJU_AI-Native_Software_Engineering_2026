## 核心論點

- 自動化的反諷(Bainbridge 1983):日常操作交給機器,人仍要在異常時接管;練手的機會變少,接管需要的本領反而更高。許願式開發的風險就在這裡。
- 光靠「感覺」得不到正確的程式碼,人和模型都一樣,一次寫幾百行時尤其如此。
- 第一道防線是不讓 bug 產生:更好的架構、不容易傷人的語言(Java 消除指標的未定義行為,Safe Rust 消除幾乎所有記憶體安全問題)、防禦性程式設計。
- 假設 bug 仍然無法消除,品質保障就是攔住兩個箭頭:Fault → Error 靠測試,Error → Failure 靠斷言。
- 絕大部分問題是靠架構避免的。模組要能脫離其他部分單獨測試,否則測試理論都派不上用場。

## 1. Fault、Error、Failure

|  | 定義 |
| --- | --- |
| Fault | 程式裡的 bug |
| Error | 執行到違反 spec 的狀態 |
| Failure | 使用者觀察得到的異常(crash、hang、錯誤輸出) |

- 兩個箭頭都不是必然:有 bug 不一定觸發 error,有 error 不一定看得到 failure。
- 先選定觀察邊界(函式、行程、整個應用):元件的 failure 可能只是整個系統內部的 error。
- Ariane 501(1996):已無用途的程式碼裡,浮點轉 16 位整數缺少越界保護;新軌道讓數值越界,慣導停機。主、備慣導用相同的軟硬體,因同一個原因先後停機。教訓:設計備份時要想它會不會被同一個條件擊穿。

## 2. 測試為什麼難,又為什麼有效

- 你的環境不是別人的環境:硬體、作業系統、編譯器、函式庫版本。lock file 能重現依賴樹,其他仍要另外考慮。
- 你的執行不是別人的執行:系統負載、時間、網路延遲、執行緒調度都是輸入。同樣的程式和輸入,交錯順序不同結果就不同。
- 測試只能證明 bug 存在,不能證明不存在(Dijkstra)。
- 但仍然極有效:程式是嚴格的數學過程,錯的程式在典型輸入上「蒙對」的機率很低(排序直接回傳原陣列,碰巧對的機率是 1/n!)。
- Agent 同樣需要執行的回饋:寫 → 跑 → 觀察 → 再改。

## 3. 測試的層次與用例設計

| 層次 | 檢查什麼 |
| --- | --- |
| 單元測試 | 一個函式、一個模組的行為是否符合 spec |
| 整合測試 | 模組接起來後,介面、協定、資料是否對得上 |
| 系統測試 | 完整系統能否在目標環境完成任務 |
| 驗收測試 | 是否滿足使用者的需求與驗收標準 |

- 介面對上不等於含義對上:Mars Climate Orbiter 一邊輸出英制、一邊當公制用,差了約 4.45 倍。
- 黑盒(從 spec 出發):等價類劃分、邊界值(長度 0、1、上限、超過上限)、決策表、狀態轉換。預期結果也是用例的一部分,先從 spec 定答案再寫 assert。
- 白盒(從程式碼出發):語句、分支、路徑覆蓋。覆蓋率高不等於正確,執行過一行不代表檢查過它的結果。把 `add` 寫成減法,呼叫一次就覆蓋了;有 assert 才抓得到。
- 再多邊界值也只涵蓋想得到的輸入;真實使用者會做你沒想過的事。

## 4. 把測試變成日常工程

- 測試金字塔:大量快速的單元測試、適量整合測試、少量端到端測試。用 stub / mock 取代難控制的依賴,但也要用真實依賴驗證整合。
- 回歸測試:修好一個 bug 就留下能重現它的用例。要先確認用例在修復前失敗、修復後通過,否則留下的是抓不到那個 bug 的測試。
- CI:每次修改自動跑測試。測試本身也要維護:結果可重複、用例互相獨立、失敗容易定位。

## 5. 架構決定可測性

- 系統越大,越難做全系統的整合測試。所有模組都要能單獨測試,介面邊界要明確;純函式能為自己的正確性負責。
- 讓依賴可控制:
  - 遊戲邏輯寫成狀態轉換,測「開槍後少一發子彈」不必啟動渲染器。
  - 時鐘和亂數當作依賴傳入,測試直接推進時間、重放戰鬥。
  - 支付重試沿用同一個冪等鍵,由服務端識別重複請求。
  - FoundationDB 把整個叢集放進確定性模擬器,故障可以重放。

## 6. 兩種找 bug 的技術

- **Differential testing**:兩份獨立實作互相檢查,手滑型的錯誤通常落在不同地方(但也可能對手冊的同一處有相同誤解)。從相同初態出發,每執行一條指令就比對狀態,在第一處分歧停下來,把「程式跑飛了」縮小到「哪條指令之後狀態開始不同」。香山處理器用同樣的方法,跑了 4 億個時鐘週期後抓到一處 CSR 狀態不一致。
- **Fuzz testing**:本質是搜尋輸入空間,只搜得到一小部分,所以給搜尋加上選擇壓力:變異輸入 → 執行 → 保留帶來新狀態轉移的輸入 → 繼續變異。覆蓋回饋決定留下誰;崩潰、斷言或差分比較負責識別錯誤。
