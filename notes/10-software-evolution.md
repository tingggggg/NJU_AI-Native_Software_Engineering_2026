## 核心論點

- 軟體有時間維度:早期只是一個精簡的 idea,每個提前設計的擴展點都在押注「未來會往這個方向變」。
- 被依賴的東西最難換。局部演算法可以淘汰,已經被大量程式碼依賴的語義很難改。
- AI 的解題能力已經夠了,缺的是 taste。表達「壞」容易,表達「好」很難,靠累積反例不保證收斂。
- 副標題「航母是怎麼造出來的」:DeepSeek Harness 像 1922 年的試驗航母,平台有了,飛機和戰鬥群的概念還在摸索。最後成功的未必是它,但圍繞 agent 的生態是方向。

## 1. 演化:哪些容易換、哪些難換

| 案例 | 發生了什麼 | 啟示 |
| --- | --- | --- |
| Linux 排程器 | O(1) → CFS → EEVDF,CFS 同時引入 scheduling classes | 策略封裝在模組邊界後面就能替換;淘汰局部演算法也是整理邊界的機會 |
| Python 2 → 3 | 明確不向後相容,停止支援從 2015 延到 2020 | 遷移成本要算上所有依賴舊行為的程式碼,這些依賴會約束後續設計 |
| Kubernetes | 核心只有「宣告期望狀態,controller 反覆調整」;CRD 與自訂 controller 把領域知識放進生態;後來移除內建的 dockershim | 核心輕、生態重;「輕」指的是責任邊界,專用適配交給生態維護,必要時也要做減法 |

- 每次修改讓專案從一個版本進入下一個版本,仍然是狀態機。
- 我們習慣用簡化版理解軟體(Linux 0.11、nano-gpt)。簡化版幫助理解機制,版本歷史則解釋那些例外從何而來。
- 原則(Parnas 1972):按可能變化的設計決定劃分模組。架構要給尚未發生的變化留下修改空間,但不必要的架構複雜性反而會約束未來。

## 2. 從解題能力到 taste

- SWE-bench 這類「有一點希望搆得到」的 benchmark,最終都會被解決。
- 現在需要的是 taste 的評估:不是 Yes / No / 分數,而是多維度的相對比較。
  - 兩份都通過測試的實作,在相同需求下比:是否貼合問題、是否容易理解、下一次修改有多貴。
  - 再給一個後續需求,看原本的優劣會不會反轉。

## 3. 從 DeepSeek Harness 的提交歷史學到的

- 設計有來由:RFC、ADR、agent notes,記錄取捨與驗收標準。
- 協作有邊界:原子提交,一個 PR 一個 worktree,有依賴就堆疊 PR。
- 驗收有層次:逐檔覆蓋率、session 回放、真實產品與發布產物驗證。
- 經驗能累積:事故補回歸測試,採納的評審意見經維護者審核後進入 skill。
- 專案總體仍由人駕馭。AI 在大空間中取樣容易迷失方向,副作用是膨脹的 repo 與意義不明的設定檔。

## 4. 為什麼「排除壞的」不夠

- 做法:找出所有「不好」的特徵並強行排除,檢驗失敗就重新取樣。有效,但有極限。
- 一條批評可以被學成很多種規則。「別寫這麼長」可能在糾正篇幅,也可能在糾正答非所問;記住「回答要簡短」,仍然沒學會當下什麼最重要。
- 被提到的詞權重會被放大,於是出現「番茄炒蛋(不放蒜版)」,而沒被提到的還有無窮多個。
- 反例越積越多仍可能不收斂(CEGIS 的反例):逐項排除只能避開已知的失敗。要追問的是,目前的設計空間裡到底有沒有想要的答案。
- 需要設計空間的跳躍(Luchins 水罐實驗):熟練的舊解法依然答對,所以繼續改良它的回饋裡,不會出現發現新解法的線索。只問 AI「怎樣改好這份答案」,就一直把「換一種答法」排除在搜尋範圍之外。
- 作者的失敗實驗:用自己所有的回信蒸餾風格,至今無法收斂。回信只保留「最後怎麼說」,沒保留「為什麼這樣說」和被放棄的選項;難的是依情境決定哪條規則優先。

## 5. 開場的閒談(教育與 AI)

- 教育循環在鬆動:AI 同時改變能力的價格(幾年練成的本領變成人人可調用的服務)與能力的證明(成品越來越難說明人的貢獻)。
- 建議:用自己的 AI trajectory 證明能力。看你何時不接受 AI、拿什麼證據改變判斷,以及同類問題第二次出現時是否做了更好的選擇。
